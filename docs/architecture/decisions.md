# Журнал решений (ADR-lite)

> Формат: `ADR-NNN · дата · статус (accepted/superseded)` → Контекст →
> Решение → Последствия. Новая запись — при любом выборе, которого нет
> в доках, и при любом отступлении от них.

## ADR-001 · 2026-07-31 · accepted — Вариант C (гибрид)

**Контекст.** Hobby-MVP на 5 преподавателей / 50 студентов, один VPS,
бюджет единицы $/мес.
**Решение.** Ядро и модель данных — свои (Compose: Next.js + Go + Postgres);
тяжёлые подсистемы — managed/OSS: LiveKit Cloud, AssemblyAI, S3,
LibreTranslate, excalidraw-complete. Медиа никогда не проходит через VPS.
**Последствия.** Низкая стоимость и простота эксплуатации; зависимость от
внешних сервисов гасится порогами апгрейда ([06-budget.md](06-budget.md)).
Снапшот исходного документа: [00-source-variant-c.md](00-source-variant-c.md).

## ADR-002 · 2026-07-31 · accepted — api и worker: один Go-модуль, два бинаря

**Контекст.** В compose api и worker — отдельные сервисы; код у них общий
(модель, store, интеграции).
**Решение.** Один Go-модуль `backend/` с `cmd/api` и `cmd/worker`, общий
`internal/`, один Dockerfile с двумя build-target'ами.
**Последствия.** Нет дублирования домена и миграций; деплой двух контейнеров
из одного образа/сборки.

## ADR-003 · 2026-07-31 · accepted — Очереди в Postgres, Redis опционален

**Контекст.** Нужны фоновые джобы (календарь, ASR, сборщик, LLM); масштаб —
единицы задач в минуту.
**Решение.** Таблица `jobs` + `SELECT … FOR UPDATE SKIP LOCKED` в worker.
Redis добавляем только если появится реальная нужда (кэш/rate-limit).
**Последствия.** Минус один stateful-сервис; транзакционность джоб вместе
с данными.

## ADR-004 · 2026-07-31 · accepted — TLS-край: host-nginx; caddy стека — HTTP-only на loopback

**Контекст.** Доки закладывали caddy единой точкой входа с TLS Let's Encrypt
([02-services.md](02-services.md), S0-1). Фактический VPS уже обслуживает
соседние проекты: 80/443 заняты системным nginx, который терминирует TLS
(certbot) и проксирует каждый стек на его loopback-порт (образец —
`barenta.wondermr.com` → caddy стека на `127.0.0.1:8080`). Домен
`lang.wondermr.com` — за Cloudflare-прокси.
**Решение.** Вписаться в паттерн хоста: caddy стека — HTTP-only (`:80`,
`auto_https off`), опубликован только на `127.0.0.1:${HTTP_PORT}` (8090);
TLS и HSTS для `lang.wondermr.com` — на host-nginx (certbot, webroot
`/var/www/html`); vhost — `/etc/nginx/sites-available/lang.wondermr.com`.
Внутренняя маршрутизация без изменений: `/api/*` → api (префикс стрипается,
пути внутри api — как в [04-api.md](04-api.md)), остальное → web.
**Последствия.** Реальный IP клиента — в `X-Real-IP` от nginx (за Cloudflare —
адрес CF, см. комментарий в vhost barenta). Новый ключ `.env`: `HTTP_PORT`.
При переезде на чистый VPS достаточно опубликовать 80/443 и вернуть
`{$DOMAIN}` в Caddyfile.

## ADR-005 · 2026-07-31 · accepted — DDL-конвенции схемы Postgres

**Контекст.** Скетч в [03-data-model.md](03-data-model.md) задаёт таблицы и
колонки, но не фиксирует тип PK, тип времени и способ ограничения
перечислений. Масштаб — hobby (≈50 пользователей), Postgres 16.
**Решение.** Для всех таблиц: PK — `bigint GENERATED ALWAYS AS IDENTITY`
(кроме чистых связок с составным PK); время — `timestamptz`; перечисления
(`users.role`, `lessons.status`, `materials.kind`, `groups.level` —
CEFR `A1, A2, B1, B2, C1, C2`) — `text` + `CHECK`
(дешевле эволюция, чем `ENUM`); служебный `created_at timestamptz NOT NULL
DEFAULT now()` у сущностей. Колонки будущих этапов из скетча
(`lessons.transcript_id`, `recording_s3_key`, `materials.s3_key`) создаются
сразу nullable, но FK на ещё не существующие таблицы не ставится —
его добавит миграция соответствующего этапа.
**Последствия.** Единообразный DDL без сюрпризов при `ALTER`; identity
не переживёт merge двух баз (не наш случай); `CHECK`-перечисления меняются
одной миграцией без пересоздания типа.

## ADR-006 · 2026-07-31 · accepted — Auth: cookie-сессии в Postgres, bcrypt

**Контекст.** S0-3 требует выбрать механизм auth: cookie-сессии или JWT.
Масштаб — 55 пользователей, один VPS, один api-процесс; план этапа прямо
предостерегает от переусложнения auth.
**Решение.** Серверные сессии в Postgres: таблица `sessions` (в БД — только
`sha256`-дайджест токена, TTL 30 дней), cookie `sid` — HttpOnly, Secure,
SameSite=Lax, Path=/. Пароли — bcrypt: в Go `golang.org/x/crypto/bcrypt`,
в seed — `pgcrypto` `crypt(..., gen_salt('bf', 12))` (форматы совместимы);
пароль seed-пользователей задаётся ключом `.env` `SEED_PASSWORD` и в git
не попадает. JWT отклонён: ревокация и logout при сессиях тривиальны,
stateless-выгоды на одном процессе отсутствуют. Новые эндпоинты этапа 0:
`POST /auth/logout`, `GET /auth/me` (нужен web-каркасу S0-5) — добавлены
в [04-api.md](04-api.md).
**Последствия.** Каждый авторизованный запрос — один SELECT сессии
(на нашем масштабе незаметно); протухшие сессии чистятся лениво при
логине владельца, глобальная уборка — периодической джобой worker'а
(долг D-15: в S1-2 периодических джоб нет, ADR-013).
Ключ `.env` `SESSION_SECRET`, заложенный планом на S0-1, удалён: при
серверных сессиях подпись не нужна. Первые Go-зависимости:
`jackc/pgx/v5`, `golang.org/x/crypto`.

## ADR-007 · 2026-08-02 · accepted — Роль admin и управление учётными записями

**Контекст.** Планы этапов 0–5 и [04-api.md](04-api.md) не содержат ни одного
эндпоинта заведения человека: `POST /groups/{id}/members` добавляет только
существующего пользователя (404, если его нет), а сами пользователи
появлялись лишь из `seed.sql`. Позвать на площадку живых студентов было
нечем — это пробел проектирования, а не отложенный на будущий этап долг.
**Решение.** Третья роль `admin` (модель ролей становится
`admin | teacher | student`, миграция `0003_roles`) и раздел управления
учётками:
- `admin` заводит и правит любого пользователя, сбрасывает пароли,
  управляет группами и составом участников;
- `teacher` заводит только студентов и правит только тех, кто состоит
  в его группах **и является студентом** (least privilege: угнанная учётка
  преподавателя не открывает все 50 студентов, а случайно попавшая
  в `group_members` staff-учётка не открывает чужой профиль и пароль);
- **состав групп меняет только `admin`** (создание группы, добавление и
  удаление участников): у `groups` нет владельца, поэтому «своя группа»
  для записи неопределима — преподаватель добавил бы себя в любую группу
  и получил бы её студентов. Чтение групп остаётся у staff: состав нужен
  для переклички на уроке;
- любой пользователь правит своё имя и меняет свой пароль (со старым).
Пароль задаётся при создании (стартовый, отдаётся человеку лично).
Саморегистрация отклонена: домен публичный.
**Заменено [ADR-008](#adr-008--2026-08-02--accepted--одноразовые-ссылки-приглашения):**
инвайт-ссылки здесь были отклонены, теперь они — основной путь, а заведение
со стартовым паролем осталось запасным.
Смена и сброс пароля удаляют все сессии владельца (дешёвая ревокация —
прямое следствие серверных сессий из ADR-006); при смене себе текущая
сессия тут же пересоздаётся, чтобы разлогинивались только прочие устройства.
Первый `admin` создаётся `seed.sql`; на живом стенде роль выдаётся
существующему аккаунту через `make psql`.
**Последствия.** Удаления пользователей нет — при `lessons.teacher_id`
и накопленной истории это отдельное решение (архивация vs каскад),
оформлено долгом D-5 (закрыт архивацией, [ADR-024](#adr-024--2026-10-26--accepted--файлы-материалов-в-r2-и-архивация-учёток-долги-d-4-d-5)). Роли проверяются `requireAnyRole`, эндпоинты
`/users` и `/auth/password` добавлены в [04-api.md](04-api.md), состав
ролей — в [03-data-model.md](03-data-model.md).

## ADR-008 · 2026-08-02 · accepted — Одноразовые ссылки-приглашения

**Контекст.** [ADR-007](#adr-007--2026-08-02--accepted--роль-admin-и-управление-учётными-записями) отклонил инвайт-ссылки в пользу стартового пароля:
почтового сервиса в стеке нет, ссылку всё равно передавать руками. Довод про
почту верен, но вывод из него был неправильный: канал передачи у ссылки и
у пароля один и тот же (мессенджер, голос), а свойства разные. Стартовый
пароль знает пригласивший, он живёт до первой смены и передаётся как рабочий
секрет; ссылка гасится в момент приёма — когда человек задал пароль, — и самого пароля не содержит вовсе; предпросмотр по ссылке её не расходует.
**Решение.** Раздел [ADR-007](#adr-007--2026-08-02--accepted--роль-admin-и-управление-учётными-записями) про отклонение инвайт-ссылок заменяется:
приглашение — основной путь, заведение со стартовым паролем остаётся
запасным. Таблица `invites` (миграция `0004_invites`): в БД только
`sha256`-дайджест токена, как у сессий ([ADR-006](#adr-006--2026-07-31--accepted--auth-cookie-сессии-в-postgres-bcrypt)); срок жизни 7 дней;
одноразовость обеспечивает `UPDATE … WHERE accepted_at IS NULL AND
expires_at > now() RETURNING` первым шагом транзакции приёма — две
параллельные попытки по одной ссылке не создадут двух пользователей.
Приглашённый сам задаёт пароль и сразу получает сессию. Публичные
эндпоинты `GET/POST /signup/{token}` (аутентификации ещё нет); выпуск,
список и отзыв — staff, с теми же границами, что у `/users`: преподаватель
зовёт только студентов и только без зачисления в группу (состав групп —
админ, ADR-007). Занятый email проверяется при выпуске, чтобы приглашённый не упирался в 409
после того, как придумал пароль. Проверка адрес не резервирует: если его
займут между выпуском и приёмом, 409 придёт на приёме — это осознанный
компромисс вместо блокировки адреса на неделю.
**Последствия.** Ссылка показывается один раз — восстановить её из БД
нельзя, только выпустить новую. Ключ `.env` `DOMAIN` становится
обязательным для api: из него собирается адрес приглашения. Рассылки
по-прежнему нет — при появлении SMTP отправка письма станет надстройкой
над этим же механизмом, без смены схемы. Отдельного rate-limit на
`/signup/{token}` нет: токен — 256 бит случайности, перебор нереалистичен;
при появлении общего троттлинга api эндпоинт попадёт под него.

## ADR-009 · 2026-08-03 · accepted — Объектное хранилище: Cloudflare R2

**Контекст.** [ADR-001](#adr-001--2026-07-31--accepted--вариант-c-гибрид) и
[05-storage-s3.md](05-storage-s3.md) закладывали AWS S3. Записи уроков — это
0.7–1.1 GB на час; их читают браузеры студентов (плеер) и AssemblyAI
(транскрибация), то есть трафик наружу пропорционален не объёму хранения,
а числу просмотров. У AWS бесплатны первые 100 GB egress в месяц, дальше
он платный; у R2 исходящий трафик бесплатен всегда.
**Решение.** Хранилище — **Cloudflare R2**, S3-совместимый API.
Проверено по документации Cloudflare:
- эндпоинт `https://<account_id>.r2.cloudflarestorage.com`, регион в SDK —
  `auto` (пустое значение и `us-east-1` алиасятся в него);
- presigned URL поддержаны для GET/HEAD/PUT/DELETE, максимальный TTL —
  7 дней (наши 30 минут проходят с запасом); POST для multipart-форм нет —
  нам он не нужен;
- `PutBucketCors` и `PutBucketLifecycleConfiguration` доступны по S3 API,
  то есть бакет настраивается тем же `aws cli` с `--endpoint-url`.

Ключи — **два токена разного назначения**: временный `Admin Read & Write`
для разовой настройки бакета и постоянный `Object Read & Write`, ограниченный
одним бакетом, — он уходит в api и в конфиг LiveKit Egress. Бакетная
конфигурация под вторым токеном недоступна, и это правильно: рабочий ключ
не должен уметь менять политику хранения.
**Последствия.** **Архивного класса у R2 нет** — только `Standard` и
`Infrequent Access`. Ступень «Glacier IR через 90 дней» из
[05-storage-s3.md](05-storage-s3.md) невыполнима; остаётся переход в IA
через 30 дней, а роль холодного хранения играет удаление видео старше
N месяцев с сохранением аудио и VTT (транскрипт ценнее сырого видео).
Файл обновлён. Порог «поставить CloudFront перед бакетом» из
[06-budget.md](06-budget.md) отпадает вместе с платным egress.
Инвариант «медиа не проходит через VPS» не затронут: presigned-механика
и запись Egress работают ровно так же.
**Токен R2 не должен иметь ограничения по IP.** Записи пишет Egress
с адресов LiveKit Cloud, а читают браузеры студентов и AssemblyAI —
перечислить эти адреса нельзя. Проверено на стенде: presigned GET,
подписанный токеном с условием `request_ip`, скачивается и с чужого
адреса, то есть на подписанные ссылки условие не распространяется;
поведение Egress-записи при таком условии не проверялось, и цена ошибки —
молча потерянная запись урока. Ограничение по IP снимаем. Возврат на AWS — смена трёх ключей
`.env` (`S3_ENDPOINT` пустеет, регион становится реальным) без правки кода:
всё различие спрятано за `S3_ENDPOINT` и `ForcePathStyle`.

## ADR-010 · 2026-08-10 · accepted — Открытые события и гостевой доступ

**Контекст.** Понадобилось звать людей со стороны: выпустить ссылку, по
которой человек представляется именем и попадает на событие, не заводя
учётку. Ни «события», ни гостей в планах 0–5 нет; «событие» в доках всюду
означает календарное событие урока, отдельной сущности домен не знает.
Текущая модель гостя не пускает трижды: участники урока — снапшот
`group_members`, `canSeeLesson` проверяет `user.ID`, `identity` в LiveKit —
это `user_id`.
**Решение.** **Событие — это урок без группы**, а не новая сущность
(миграция `0005_open_events`): `lessons.group_id` становится nullable,
добавляется `title` для названия там, где нет группы, и `CHECK`, что
название берётся хоть откуда-то. Так переиспользуются комната `lesson-{id}`,
Egress, запись в R2, плеер и будущий транскрипт — отдельная таблица `events`
удвоила бы этот код ради полей, которые совпадают.

Гость — четвёртая роль в `users`, строка заводится при переходе по ссылке
вместе с записью в `lesson_participants`. Это дороже, чем безучётный токен,
но зато `canSeeLesson`, `identity` для LiveKit и маппинг спикеров (S2-5)
работают без единой правки. Пароля у гостя нет — войти второй раз он
не может; сессия живёт до конца события, дальше ссылка ведёт в никуда.
В списках людей админ-кабинета гости не показываются: 50 студентов
не должны тонуть в случайных посетителях.

**Ссылка многоразовая** — этим она отличается от одноразовых приглашений
([ADR-008](#adr-008--2026-08-02--accepted--одноразовые-ссылки-приглашения)):
по приглашению приходит один человек и заводит учётку, по гостевой ссылке
приходят все и учёток не заводят. Хранится, как всё остальное, только
`sha256`-дайджест; одна ссылка на событие, отзыв — обнуление, перевыпуск —
новый токен.
**Последствия.** Гость попадает в запись и в транскрипт, поэтому на странице
входа он видит предупреждение о записи до того, как назовётся, — иначе мы
пишем человека, который об этом не знал. Роль `guest` расширяет `CHECK`
`users.role` до четырёх значений. Открытые события не попадают в календари
(S1-1 рассылает по `attendees` из группы) — для событий это осмысленно.
Ссылка действует до конца события: пускать в комнату после `processing`
и так нельзя (S1-4). Правила события держит и схема (миграция
`0006_event_constraints`): непустой `title` и гостевая ссылка — только
у урока без группы. Вход гостя читает урок `FOR SHARE`, поэтому отзыв
и перевыпуск отключают старую ссылку строго, без окна гонки.

## ADR-011 · 2026-10-24 · accepted — security validation in CI

Run real HTTP/SQL security tests against disposable Postgres, retain the LiveKit signing contract tests, and build/typecheck the web application. Audit complete Go/npm dependency inventories and the actual Compose runtime images, including every severity and unfixed findings. Source secrets, missing inventories, and scanner errors block. Pin actions and scanner versions. PR checks do not access production services or credentials. Package-scoped Go advisories require artifact-specific applicability evidence; a blanket ignore or reduced severity threshold is unacceptable.

Bind fresh package-level source analysis to exact source and lockfile contents, and binary analysis to all Go executables in the exact scanned OCI image. Require actual affected-code controls, retain complete raw inventories and proof artifacts, and reject stale, incomplete or mismatched evidence. Rebuild the complete standard Caddy distribution and PostgreSQL 16's gosu with patched dependencies while preserving upstream module-version metadata, the existing entrypoints, API nonroot user and health checks. Keep Node 22 with Alpine 3.22's versioned `nodejs~22` runtime package; keep npm/Yarn in build stages only. Keep all built-in secret rules active, disable the Markdown allow rule, and require a generated README token control to fail; redact secret values in retained artifacts without dropping findings.

## ADR-012 · 2026-10-26 · accepted — Запуск записи: статус live только вместе с Egress

**Контекст.** В S1-5 `room_started` сначала переводил урок scheduled → live
(это же условие делало вызов идемпотентным), а потом запускал Egress.
Ошибка запуска только логировалась, вебхук отвечал 200: урок оставался
live без записи, а повторная доставка получала `ErrNotFound` — записи
у такого урока не появилось бы уже никогда (ревью PR #9).
**Решение.** Переход в live и запуск Egress — одна транзакция
(`store.StartLessonRecording`): строка урока захватывается
`FOR UPDATE SKIP LOCKED`, Egress запускается под захватом, переход
фиксируется только после успешного ответа LiveKit. Ошибка — откат, урок
остаётся scheduled, вебхук отвечает 503, и LiveKit повторяет доставку
(livekit-server — ограниченное число раз, с паузами). Запуск записи
вызывает и `participant_joined`: если повторы кончились или `room_started`
не дошёл (api перезапускался), запись запустит следующий вошедший.
Отдельную колонку под «захват записи» не заводим: live у нас и так значит
«комната открыта и запись идёт» — без хранилища урок и раньше оставался
scheduled при открытой комнате, страница урока выводит фазу «идёт»
по времени (`web/lib/lesson-phase.ts`), а комната пускает и в scheduled.
**Последствия.** Пока запись не запущена, урок в scheduled и его можно
перенести или отменить — как и без хранилища. Строка урока занята на время
вызова Egress (не дольше 15 с таймаута клиента); параллельные доставки
её пропускают, не дожидаясь. Неопределённый исход — LiveKit запустил
Egress, но ответ потерялся или транзакция не зафиксировалась — приведёт
к повторному запуску: второй Egress пишет в тот же ключ и тратит лишние
минуты Egress. На hobby-масштабе это дешевле сверки через `ListEgress`.
Сбой уже идущей записи (`egress_ended` с `EGRESS_FAILED`) по-прежнему
только логируется.

## ADR-013 · 2026-10-26 · accepted — Очередь jobs: S1-2 без calendar_sync, джоба-плейсхолдер

**Контекст.** S1-2 по плану — worker, очередь `jobs` и первая джоба
`calendar_sync`. Но calendar_sync держится на OAuth-токенах преподавателей
(S1-1), а S1-1 уехал за MVP (порядок этапа в [INDEX](../tasks/README.md)).
Модель данных задаёт колонки `jobs`, но не семантику: что такое захват,
что делать с выполненной джобой и с исчерпанными попытками.
**Решение.** S1-2 закрывается без calendar_sync — долг D-7, закрывает S1-1.
Первая джоба — плейсхолдер `recording_ready`, явная точка вставки ASR
из S1-5: `egress_ended` пишет путь записи, `status=processing` и ставит
джобу одной транзакцией, хендлер переводит урок в `done`. S2-1 заменит её
джобой `asr_submit`. Семантика очереди (`internal/jobs`):
- захват — аренда: один `UPDATE … WHERE id = (SELECT … FOR UPDATE SKIP
  LOCKED)` ставит `locked_at`/`locked_by` и `attempts + 1`, хендлер
  работает вне транзакции. Захват старше двух таймаутов хендлера (2 × 5 мин)
  брошен упавшим worker'ом и подбирается снова; итог попытки пишется
  только при совпадении `locked_by` и `attempts`, поэтому запоздавший
  владелец чужой захват не испортит;
- выполненная джоба удаляется; ошибка — `last_error` и повтор через
  1 мин с удвоением до 1 ч; после 8 попыток (≈ 2 ч) ставится `failed_at`:
  джоба остаётся для разбора и больше не берётся. `failed_at` и служебный
  `created_at` (ADR-005) — две колонки сверх модели данных;
- доставка at-least-once, хендлеры идемпотентны; worker берёт только
  известные ему kind — джоба нового kind ждёт выката своего хендлера;
- SIGTERM: новые джобы не берутся, текущей даётся 20 с, затем её прерывают
  и возвращают в очередь без списания попытки (`stop_grace_period: 30s`);
- пустая очередь опрашивается раз в секунду; LISTEN/NOTIFY на нашем
  масштабе не нужен. Новых зависимостей нет — только pgx.
**Последствия.** Урок без работающего worker'а застревает в `processing`:
worker в compose обязателен. Сбой транзакции `egress_ended` (БД
недоступна, нет таблицы `jobs`) api отвечает LiveKit 503, и тот повторяет
доставку; условие на статус урока делает повтор безопасным. Повторы
у LiveKit ограничены, поэтому миграция `0007_jobs` всё равно выкатывается
раньше api: иначе, исчерпав их, путь записи теряется. Мёртвые джобы видны
запросом `failed_at IS NOT NULL`; оживить — обнулить `failed_at` и
`attempts`. Healthcheck у worker'а не заведён: HTTP у него нет, упавший
процесс поднимает `restart`. Глобальная уборка протухших сессий
из ADR-006 не сделана: ей нужны периодические джобы, а их в S1-2 нет —
долг D-15.

## ADR-014 · 2026-10-26 · accepted — Бэкапы Postgres: retention 7/30 и свой токен хранилища

**Контекст.** S1-7 и [05-storage-s3.md](05-storage-s3.md) задают ночной
`pg_dump | zstd` → `backups/pg/{date}.dump.zst` с «retention 7 дневных /
30 дней», не говоря, что хранится между 7-м и 30-м днём. Второй вопрос —
доступ. Токен R2 `S3_*` ([ADR-009](#adr-009--2026-08-03--accepted--объектное-хранилище-cloudflare-r2))
api передаёт LiveKit в каждом egress-запросе, то есть копия лежит у третьей
стороны и умеет читать и удалять всё в бакете. В дампе — bcrypt-хэши
паролей и email всех учёток, sha256-дайджесты сессий и ссылок, позже —
зашифрованные refresh-токены Google (S1-1).
**Решение.** Retention: все копии последних 7 суток (дата в имени — UTC);
от 7 до 30 суток — по одной на ISO-неделю, самая свежая в неделе (обычно
воскресная, при пропуске — последняя из имеющихся); старше 30 суток —
удаляются. В устоявшемся режиме это ~11 копий. Чистит сам
`deploy/backup-pg.sh` после проверенной выгрузки; объекты с другими
именами под `backups/pg/` (ручные копии) не трогает; если копии моложе
7 суток нет, чистку не делает и падает. Lifecycle-правило для
`backups/pg/` не ставим: «одну в неделю» им не выразить, а истечение
по возрасту продолжает работать, когда бэкапы перестали делаться, —
через 30 дней не осталось бы ни одной копии.

Доступ: ключи `BACKUP_S3_*` перекрывают `S3_*`, целевая схема — отдельный
бакет и отдельный токен Object Read & Write только на него. Тогда копия
токена у LiveKit не видит дампов, а скрипт бэкапа — записей. Пока все
`BACKUP_S3_*` пусты, скрипт работает под `S3_*` и пишет предупреждение
в журнал: бэкап под общим токеном лучше, чем никакого. Задан хоть один
`BACKUP_S3_*` — обязателен свой `BACKUP_S3_BUCKET`, и общим местом
считается тот же бакет на том же эндпоинте, а не только тот же ключ:
иначе ключи без бакета молча писали бы дампы в бакет записей. Клиентское
шифрование (age/gpg) отложено: оно закрывает чтение дампа держателем
токена, но не удаление, а ключ расшифровки — ещё одна точка отказа
для RTO «за час»: потерян ключ — потеряны все копии. Вернуться к нему,
если отдельный токен невозможен или в БД появятся секреты в открытом виде.

Инструменты: aws cli — одноразовый контейнер из закреплённого digest'ом
`amazon/aws-cli:2.32.7` (им уже работали с R2 стенда), ключи — через
окружение, не в командной строке; zstd — на хосте; pg_dump и pg_restore —
внутри контейнера postgres по локальному сокету, пароль БД скриптам
не нужен. Новых сервисов и runtime-образов в compose нет, сканирование
ADR-011 не меняется. Скрипты в CI проверяет shellcheck
(`koalaman/shellcheck:v0.10.0`, закреплён digest'ом, job `shell`
в `ci.yml`), решение retention — `scripts/test_backup_retention.py`.

Целостность: держатель токена хранилища может подложить объект вместе
с метаданными, поэтому sha256 в метаданных — защита от порчи, не от
подмены. Проверенные выгрузки записываются в манифест на VPS вне бакета
(`/var/lib/lingua-backup/manifest`, только root: ключ, sha256, размер),
и `deploy/restore-pg.sh` сверяет копию с ним; копию без записи
в манифесте (или без sha256 вовсе, когда манифеста нет) разворачивает
только с `--insecure-no-verify`. Без `--date`/`--key` берётся самая
свежая ночная копия не позже сегодняшней даты, а в рабочую базу
(`POSTGRES_DB`) — только явно названная.
**Последствия.** Выгрузка идёт во временный `backups/pg/incoming/…`,
скачивается обратно и сверяется по sha256 и только потом копируется
внутри хранилища в ночной ключ; у R2 исходящий трафик бесплатен, на
объёме дампа hobby-базы это копейки. Повторный прогон в тот же день
заменяет копию дня только проверенной. Ночные копии с датой позже
сегодняшней чистка не удаляет, но называет и завершается с ошибкой.
Манифест живёт на VPS: при переезде на новую машину его копию нужно
держать рядом с `deploy/.env`, иначе сверка — только по метаданным.
Восстановление — одной транзакцией; непустую базу скрипт перезаписывает
только с `--force`.
Роли и гранты из дампа не переносятся — объекты получает учётка контейнера
(`POSTGRES_USER`), других ролей у стенда нет. Расписание — systemd-таймер
на VPS, 03:30 UTC; провал виден как `failed`-юнит, оповещения нет. Пока
владелец не завёл бакет и токен для бэкапов — долг D-8.

## ADR-023 · 2026-10-26 · accepted — Google Calendar: OAuth2 с PKCE, AES-GCM для токена, свой id события

**Контекст.** S1-1 и джоба `calendar_sync` из S1-2 (долг D-7). Доки задают
web flow только для преподавателей, scope `calendar.events`, шифрованный
refresh token «примитив — в ADR», `events.insert/update/delete` и
идемпотентность через `gcal_event_id`. Не заданы библиотека, защита flow,
формат шифртекста и ротация ключа, способ сделать идемпотентным сам insert
(ответ Google может потеряться после создания события) и удаление события
при отмене — строка урока при отмене удаляется. В
[04-api.md](04-api.md) был `POST /auth/google/callback`, а Google
возвращает браузер на redirect URI обычным переходом (GET).
**Решение.**
- Зависимость — `golang.org/x/oauth2` v0.37.0, только корневой пакет:
  обмен кода, PKCE, обновление access token. Calendar API v3 — три
  REST-вызова своим кодом (`internal/gcal`). `google.golang.org/api`
  не берём: ради трёх вызовов он тянет gRPC и OpenTelemetry;
  `x/oauth2/google` — тоже, он тянет `cloud.google.com/go/compute/metadata`
  ради двух адресов.
- Эндпоинты, все под ролью teacher (уроки создаёт только он):
  `GET /auth/google` — статус, `POST /auth/google/start` — адрес экрана
  согласия, `GET /auth/google/callback` — обмен кода и редирект на
  `/account?google=<итог>`, `DELETE /auth/google` — отключение. Старт —
  POST: cookie сессии SameSite=Lax не уходит в межсайтовом POST.
- Защита flow: `state` (256 бит, Google требует защиту от CSRF) и PKCE S256
  (RFC 9700 рекомендует его и конфиденциальным клиентам; S256 объявлен
  в discovery-документе Google). Оба значения — в cookie `google_oauth`
  (HttpOnly, Secure, SameSite=Lax, Path `/api/auth/google`, 10 мин),
  гасится после любого исхода callback. `access_type=offline` и
  `prompt=consent` — refresh token приходит и при повторном подключении.
  Выданный scope проверяется: экран согласия Google позволяет снять
  галочку календаря.
- Хранение: `users.google_refresh_token bytea` (миграция `0012`) —
  AES-256-GCM, ключ `GOOGLE_TOKEN_KEY` (base64 от 32 байт), формат
  версия (1 байт) ‖ nonce (12) ‖ шифртекст с тегом, в associated data —
  id пользователя: шифртекст из чужой строки не расшифруется.
- Ротация ключа: замена `GOOGLE_TOKEN_KEY` делает сохранённые токены
  нечитаемыми — `/account` показывает «не подключён», calendar_sync
  пропускает уроки со строкой в журнале, преподаватели подключаются заново.
  Для пяти человек это дешевле схемы из двух ключей. Байт версии оставляет
  место для неё (id ключа, старый ключ только на чтение, перешифровка при
  использовании), если преподавателей станет много.
- Отключение стирает токен и затем отзывает его в Google
  (`oauth2.googleapis.com/revoke`); отзыв по возможности — сбой только
  в журнале. Отозванный в Google или истёкший токен (`invalid_grant`
  при обновлении) worker снимает сам.
- `calendar_sync` ставится в транзакции создания, переноса и отмены урока
  и только если у организатора есть токен. Проверка — `FOR SHARE` на его
  строке users первой в транзакции: порядок блокировок users → lessons тот
  же, что у подключения, и урок, созданный одновременно с подключением,
  не теряется. Подключение ставит джобы для всех будущих `scheduled`-уроков
  преподавателя — заведённые раньше тоже попадают в календарь.
- Идемпотентность: id события назначаем сами в той же транзакции —
  `gcal_event_id` = 32 hex-символа `gen_random_uuid()` (алфавит base32hex,
  который принимает Calendar API). Хендлер делает insert с этим id;
  409 duplicate → update (так советует справочник ошибок Calendar API);
  404/410 на удалении — успех. Событие строится из текущего состояния урока,
  поэтому порядок и повторы джоб не важны. Payload — `{"lesson_id"}`,
  у отмены ещё `teacher_id` и `event_id`: строки урока к запуску уже нет.
  После insert/update хендлер проверяет, что урок не отменили за время
  вызова, иначе удаляет событие сам.
- Событие: основной календарь (`primary`) преподавателя; summary —
  название события или имя группы; description —
  `https://<DOMAIN>/lesson/{id}`; attendees — `lesson_participants` без
  гостей (синтетический email, ADR-010) и без самого преподавателя;
  `sendUpdates=all` во всех трёх вызовах.
- Без любого из трёх ключей интеграция выключена (`gcal.New` → nil, как
  `storage.New`): старт — 503, `/account` пишет «недоступно», worker снимает
  calendar_sync со строкой в журнале. Битый ключ — ошибка старта api
  и worker, как пустой регион у storage. Worker с ключами требует `DOMAIN`.
**Последствия.** `update` перезаписывает событие целиком (patch-семантики
у метода нет): правки руками в Google при переносе теряются. Состав группы,
изменённый после создания урока, в календарь не попадает — участники урока
и так снапшот. Access token обновляется в каждой джобе — лишний запрос
к Google, на нашем масштабе незаметно. Откат `0012` удаляет токены
и ожидающие calendar_sync. С настоящим Google ничего не проверено: OAuth-
клиента у стенда нет, всё покрыто httptest-фейком (долг D-13).

## ADR-024 · 2026-10-26 · accepted — Файлы материалов в R2 и архивация учёток (долги D-4, D-5)

**Контекст.** D-4: материал несёт только `body_md`. S1-3 и
[05-storage-s3.md](05-storage-s3.md) закладывают `materials.s3_key` и
раскладку `materials/{lesson_id}/…`, но не говорят, как файл попадает
в бакет, кто его проверяет и какие файлы принимаются. D-5:
[ADR-007](#adr-007--2026-08-02--accepted--роль-admin-и-управление-учётными-записями)
оставил открытым удаление учёток: на пользователя ссылаются уроки
(`teacher_id`), участие, приглашения и вся будущая история (транскрипты,
словарь, SRS) — каскад стёр бы её, а без каскада удалить нельзя.
**Решение — файлы.** Один файл на материал: рядом с `s3_key` миграция
`0013_material_files_archive` кладёт `file_name`, `file_content_type`,
`file_size`, `file_uploaded_at`; `CHECK` — метаданные целиком или никаких,
ключ только под `materials/{lesson_id}/`. Отдельная таблица не нужна:
несколько файлов — это несколько материалов. Файл идёт браузер ↔ R2
напрямую (медиа-инвариант):
- `POST /lessons/{id}/materials` (или `/homework`) с `file: {name,
  content_type, size}` — только преподаватель урока. api проверяет тип
  по белому списку (PDF, DOCX, PPTX, TXT, PNG, JPEG, WebP, MP3, M4A, OGG,
  MP4) и размер (до 50 MiB), сам выбирает ключ
  `materials/{lesson_id}/<128 случайных бит>.<ext>` — имя от клиента
  в путь не попадает — и подписывает PUT на 10 минут. В подпись входят
  `Content-Type`, `Content-Length` и `Content-Disposition: attachment`
  с именем файла (RFC 2231): другой тип или длина дают 403. Подпись типа
  R2 документирует, про длину документации нет — поэтому её сверяет ещё
  и подтверждение;
- `POST /materials/{id}/confirm` — HEAD объекта: нет — 409, заготовка
  остаётся; размер или тип не совпали — объект и материал удаляются, 422.
  До подтверждения файл видит только преподаватель;
- `GET /materials/{id}/url` — presigned GET на 30 минут с границей урока
  (преподаватель и участники). Имя для сохранения хранилище отдаёт из
  записанного при загрузке `Content-Disposition`: параметр
  `response-content-disposition` в документации R2 не значится;
- `DELETE /materials/{id}` — сначала объект, потом строка, чтобы сбой
  не оставил файла без ссылки. Отмена урока удаляет материалы каскадом,
  а объекты — api после фиксации; сбой — строка в журнале.
CORS бакета получает второе правило: `PUT` с заголовками `Content-Type`
и `Content-Disposition`. В api хранилище спрятано за интерфейсом
`objectStore` — тесты подставляют фейк; новых зависимостей нет.
**Решение — архив.** Удаления нет, есть архивация: `users.deactivated_at`.
`POST /users/{id}/deactivate` ставит отметку и гасит все сессии одной
транзакцией, `POST /users/{id}/reactivate` снимает её — вход по прежнему
паролю. Права — как на правку (ADR-007): админ — любую учётку, кроме
своей; преподаватель — только студентов своих групп, staff ему недоступен.
Логин архивного после верного пароля — 403 `account_deactivated`, с
неверным — обычный 401: знающему пароль честный ответ ничего не раскрывает.
Поиск сессии отсекает архивных, поэтому сессия, дописанная логином в гонке
с архивацией, не пускает. `GET /users` по умолчанию без архива,
`?archived=1` — только архив. Из групп человек не убирается (в составе
есть отметка `archived`), но в снапшот новых уроков не попадает.
**Последствия.** Объект, залитый, но не подтверждённый, лежит в бакете,
пока заготовку не удалят; web убирает её сам при сбое загрузки, заливать
может только преподаватель. Откат `0013` оставляет материалы текстовыми
и объекты в бакете. Бакет стенда настроен до D-4 и PUT не пускает —
загрузка заработает после повторного `deploy/s3-bootstrap.sh` (долг D-14).
Уроки архивного преподавателя остаются за ним, выпущенные им приглашения
действуют — их отзывает админ; передача уроков другому — отдельная задача.
