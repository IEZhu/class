# Интеграция: Google Calendar

> Этап 1 (S1-1, S1-2). Календарь — канал доставки расписания студентам:
> событие с attendees прилетает в их личные календари автоматически.

## OAuth2

- Web flow **только для преподавателей**, scope `calendar.events`:
  `/account` → `POST /auth/google/start` → экран согласия Google →
  `GET /auth/google/callback` → `/account?google=<итог>`. Защита — `state`
  и PKCE S256 в cookie `__Host-google_oauth`, запечатанном AES-GCM для
  начавшего подключение преподавателя (подложенный или чужой cookie
  отклоняется до обмена кода), `access_type=offline` + `prompt=consent`
  ([ADR-023](../decisions.md)). Callback проверяет сессию сам и всегда
  отвечает редиректом: без сессии — на `/login`. Redirect URI —
  `https://<DOMAIN>/api/auth/google/callback`, настройка клиента — в
  [deploy/README.md](../../../deploy/README.md#google-calendar-s1-1).
- Refresh token — в `users.google_refresh_token`, **шифрованный**:
  AES-256-GCM, ключ `GOOGLE_TOKEN_KEY` в `.env`, id пользователя
  в associated data. Смена ключа — преподаватели подключаются заново;
  при утечке `.env` ещё и смена client secret
  ([deploy/README.md](../../../deploy/README.md#google-calendar-s1-1)).
- Отключение (`DELETE /auth/google`) стирает токен и отзывает его в Google
  (отзыв снимает весь доступ приложения к аккаунту); не вышло — ответ
  `{"revoked": false}`, и `/account` просит снять доступ в аккаунте Google
  вручную. Уже созданные события отключение **не удаляет**: они остаются
  у преподавателя и участников. Отмены, сделанные без подключения, ждут
  в очереди и доходят до Google после повторного подключения того же
  аккаунта, переносы — синхронизацией будущих уроков при подключении.
  Подключение другого аккаунта создаёт будущие уроки в новом календаре
  заново, а события прежнего не трогает.
- Без ключей `GOOGLE_*` подключение недоступно (503, на `/account` —
  «недоступно»), calendar_sync пропускает создание и перенос (удаления
  ждут), остальной стенд работает.
- **GCP-приложение перевести из Testing в Production сразу**, иначе refresh
  token живёт 7 дней. Unverified + sensitive scope = warning-экран и лимит
  ~100 пользователей — для нас приемлемо.

## Операции (worker, джоба calendar_sync)

| Действие на платформе | Вызов Calendar API |
|---|---|
| Создание урока | `events.insert`: `attendees` = email участников группы, `sendUpdates: all`, description = `https://platform/lesson/{id}` |
| Перенос урока | `events.update` |
| Отмена урока | `events.delete` |

`gcal_event_id` хранится в `lessons`; джобы идемпотентны (повторный запуск
не создаёт дубликат события): id события назначаем сами в транзакции урока,
insert с занятым id получает 409 и становится update, удаление отсутствующего
события (404/410) — успех. Джоба ставится в той же транзакции, что
создание, перенос или отмена. Создание и перенос — только если у
организатора подключён календарь (подключение ставит джобы для его будущих
уроков), без рабочего токена worker их пропускает. Отмена ставит удаление
всегда, когда у урока есть `gcal_event_id`; без рабочего токена оно не
пропускается, а ждёт (повторы, затем мёртвая джоба), и подключение
возвращает его в работу. Календарь — основной (`primary`) календарь
преподавателя; `attendees` — участники урока без гостей (у них
синтетический email) и без самого преподавателя. Отозванный в Google
доступ (`invalid_grant`) снимает подключение. Каждый вызов Calendar API
ограничен 15 с.
